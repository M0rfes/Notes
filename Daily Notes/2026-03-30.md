## 🧠 Brain Dump
Read about [[LLMs/Quantisation]]  where we truncate the weight bit size to trade accuracy for speed. A smaller number format requires less RAM to run the model with the same parameters with higher precision number

An example of Quantisation is [[TurboQuant]]

Read about [[LLMs/TokenCashing]] We can do token cashing at 2 levels:
- Prompt / prefix caching (API level):  
    The service notices that the beginning of your new request is identical to part of a previous request, so it reuses stored internal state for that shared prefix instead of recomputing it. This reduces billed tokens and latency for repeated or slowly evolving prompts (e.g., chat histories or “template + changing suffix”).
    
- KV caching (model level):  
    Inside a transformer, each token is turned into queries, keys, and values (Q, K, V). During generation, keys and values for old tokens never change, so the model can cache them and only compute Q, K, V for the newest token, then attend to “cached K/V + new K/V” instead of reprocessing the whole sequence every step.

[[vLLM]] Core inference engines (with KV cache) [[LMCache]] KV‑cache specific tooling

Skills and MCP rely on adding the metadata about the tool in the system prompt. This is fine for cloud LLMs with 1M+ token space, but not for local LLMs. These will quickly eat all the tokens, and we will have no tokens left for inference, so the idea is to have an [[LLMs|LLM]] + [[SLMs|SLM]] combo. where the main LLM is stateful and has only one tool, `discover_took (task: string)->MCP|Skill`. and a stateless SLM that has a list of all the tools; this model will return the MCP or skill info that the main model. This approach can have the advantage of loading only the skills that are needed. The challenge is to teach the main model to use the `discover_task` tool cause the model might not use the tool at all or overuse it and call it even when not needed. So we might have to use [[RL]] to teach the model to use the `dicover_tool`

With 10 tokens, we calculate 100100 interactions. With 100,000 tokens, we must calculate and store 10 billion interactions.

This quadratic growth is why context windows are limited. Doubling the context length quadruples the computation, making it one of the Transformer's main bottlenecks. The architecture is brilliant at understanding relationships, but expensive at scale.
